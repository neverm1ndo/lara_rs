# ADR-0005: проект UDS-контракта готовности primary

- Статус: `Proposed`
- Дата: 2026-11-07
- Связанные решения: [ADR-0001](0001-server-instance-control-plane.md),
  [ADR-0004](0004-release-e-incidents-and-recovery.md)
- Результат Release E: согласуемый проект протокола; реализация и пилот не входят
  в Release E.

## Контекст и граница

Игровой плагин ещё не реализован. Primary может работать под старым supervisor
с `management = "external"`, а системный `InvocationID` в таком режиме
отсутствует. UDS сообщает состояние приложения, но не является источником
истины о жизни процесса, причине завершения или успешности lifecycle-команды.
Контракт нужен до реализации Rust adapter и плагина, чтобы обе команды могли
согласовать одинаковые сообщения и сценарии отказа.

## Предлагаемый протокол v1

Lara создаёт слушающий Unix stream socket для **одного** зарегистрированного
primary; плагин подключается к нему. Путь сокета задаётся локальной
конфигурацией и не публикуется через HTTP или capability manifest. Каталог
создаётся с доступом только Lara и учётной записи игрового сервера; права
плагина на весь `/run/lara` или на секреты `/etc/lara` из этого не следуют.
При старте Lara удаляет лишь собственный устаревший socket node после проверки
типа и владельца, затем создаёт новый; работающий socket другого процесса
не перехватывается. Плагин переподключается с ограниченным backoff после
перезапуска Lara.

Каждое сообщение — UTF-8 JSON с четырёхбайтовой длиной в сетевом порядке.
Максимум 4096 байт на сообщение; превышение, неверный JSON, неизвестный тип
или версия завершают соединение. В одном соединении допускается один
handshake и один последовательный поток heartbeat; команды управления
процессом по этому каналу не передаются.

1. Плагин отправляет `hello` с `protocolVersion: 1`, `instanceId`, новым
   случайным `sessionId` и, если доступен, `invocationId`. `sessionId` — UUID
   на **каждый запуск процесса**; он не заменяет проверку процесса Lara.
2. Lara проверяет `SO_PEERCRED` (UID, GID, PID), ожидаемую учётную запись,
   зарегистрированный instance и отсутствие уже принятого активного сеанса.
   Для systemd-managed primary Lara независимо читает D-Bus `MainPID` и
   `InvocationID` и сверяет их с peer PID и сообщением. Для external primary
   `invocationId` отсутствует; Lara связывает сеанс с peer PID и временем
   старта процесса, прочитанным из `/proc`, и не объявляет такой процесс
   systemd-наблюдаемым. `hello` не доверяется как подтверждение личности.
3. Lara отвечает `hello_ack` с `protocolVersion`, тем же `sessionId`,
   `heartbeatIntervalMs: 5000` и `heartbeatTimeoutMs: 15000`. Плагин
   начинает heartbeat только после подтверждения.
4. Плагин отправляет `heartbeat` с `sessionId`, возрастающим `sequence`
   (начиная с 1) и `ready: true|false`. `ready` означает, что приложение
   завершило собственную инициализацию и способно обслуживать игроков.
   Время получения фиксирует Lara; время, указанное плагином, не служит
   источником истины. Lara отклоняет повторный или убывающий sequence.

Пример сообщений (показано содержимое одного frame без префикса длины):

```json
{"type":"hello","protocolVersion":1,"instanceId":"liberty","sessionId":"ba6dff5e-ef10-4b34-b0f2-3f17e137f0cb","invocationId":null}
{"type":"hello_ack","protocolVersion":1,"sessionId":"ba6dff5e-ef10-4b34-b0f2-3f17e137f0cb","heartbeatIntervalMs":5000,"heartbeatTimeoutMs":15000}
{"type":"heartbeat","sessionId":"ba6dff5e-ef10-4b34-b0f2-3f17e137f0cb","sequence":1,"ready":true}
```

При смене версии без согласованной поддержки Lara закрывает соединение с
диагностикой в своём журнале. Неизвестные поля v1 игнорируются; смысл
существующих полей и enum/type не меняется без новой версии протокола.

## Отображение в состояния Lara

- До валидного `hello` readiness — `unknown`, даже если socket открыт.
- После `hello_ack` и до первого heartbeat readiness — `not_ready`.
- Последний своевременный `heartbeat ready=true` даёт `ready`; `false` —
  `not_ready`.
- При закрытии соединения, нарушении протокола или превышении timeout
  readiness становится `unknown` до нового принятого сеанса. Смена
  `sessionId`, PID или systemd `InvocationID` сбрасывает прошлую готовность.
- Если есть достоверный systemd snapshot с неактивным процессом, процесс
  остаётся неактивным независимо от UDS. Для external primary отсутствие UDS
  **не** доказывает остановку или падение процесса.

Изменения readiness публикуются через существующий instance state contract.
Они не создают incident об отказе процесса и не заполняют `lastTermination`.
Отдельный инцидент о деградации приложения потребовал бы собственного
классификатора и решения о порогах; этот проект его не вводит. Подробный
статус primary видит Developer; уведомление Admin и Challenger о restart
появится только при достоверном process evidence, а не по потере heartbeat.

## Проверки перед принятием контракта

Команды Lara и плагина должны согласовать значение `ready`, идентичность
Unix-пользователя и путь сокета, доступность `INVOCATION_ID` внутри игрового
процесса, способ определения PID при многопроцессном плагине, формат ошибок
handshake и допустимые задержки в реальной игровой нагрузке. Проверить
переподключение после рестарта Lara, рестарт игры с повторно выданным PID,
старый heartbeat после смены сеанса, таймаут, два одновременных подключения,
запуск external primary без systemd и отказ прав на сокет.

После согласования и тестового плагина этот ADR можно принять либо заменить
обновлённым решением. Ни backend, ни плагин не должны считать данный draft
обязательным production-протоколом до совместной проверки.
