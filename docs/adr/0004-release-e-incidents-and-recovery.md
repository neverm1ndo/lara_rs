# ADR-0004: Release E — инциденты и восстановление наблюдения

- Статус: `Proposed`
- Дата: 2026-11-07
- Связанные решения: [ADR-0001](0001-server-instance-control-plane.md),
  [ADR-0002](0002-release-b-lifecycle-and-cli.md),
  [ADR-0003](0003-release-c-multi-instance-configuration.md)

## Контекст

Release C реализовал instance-scoped configuration, управление файлами
auxiliary, загрузку бинарных артефактов по точному allowlist и изоляцию
файловых корней. Старые `/configuration/...` удалены без compatibility alias:
клиент ещё не использовал этот маршрут. Поэтому прежний список Release D
`multi-instance files` уже закрыт Release C, а alias отменён принятым
решением ADR-0003.

После Release B Lara уже наблюдает systemd-managed auxiliary и хранит lifecycle
operations. Поэтому пункт старого плана Release E `Systemd observer` выполнен.
Однако текущее состояние после восстановления процесса не даёт
полной истории отказов, произошедших ночью или пока Lara была выключена.
Существующее поле `incident_tracking` и capability `lara.incidents.v1` ещё не
означают наличие журнала инцидентов. Primary в production может оставаться
`management = "external"`; UDS-плагин игрового сервера пока не готов.

## Решение о границе релиза

Release E посвящён надёжности наблюдения за **systemd-managed auxiliary**:

1. Долговечный журнал инцидентов в MongoDB с раздельными состояниями отказа
   и расследования.
2. Корреляция systemd state transitions с запланированными lifecycle
   operations и обнаружение неожиданного отказа или рестарта.
3. Восстановление пропущенных фактов из persistent journald с checkpoint,
   дедупликацией и явной отметкой о пробеле, если журнал недоступен.
4. HTTP API истории, фильтрации и подтверждения расследования, доступный
   Developer. Информация сохраняется независимо от Socket.IO-подключения.
5. Role-aware realtime: подробности всех инстансов видит Developer; событие
   auxiliary не раскрывается Admin и Challenger.
6. Диагностика `lara doctor`, OpenAPI, тесты восстановления и Linux smoke.

UDS handshake и readiness primary требуют согласованного протокола с
разработчиками игрового плагина. Они планируются отдельным шагом после
согласования протокола и готовности плагина. Release E не требует переводить
primary на systemd и не делает вывод о причине падения primary из отсутствия
UDS-соединения. До появления источника process evidence для external primary
автоматические инциденты по нему не создаются.

## Источники фактов

- Systemd D-Bus даёт актуальное состояние и быстрые переходы. Для идентичности
  запуска используются unit и `InvocationID`, для evidence — `Result`,
  `ExecMainCode`, `ExecMainStatus`, `NRestarts` и временные метки, если доступны.
- Journald восстанавливает пропущенные переходы после разрыва наблюдения.
  Курсор хранится только после долговечной фиксации обработанных фактов.
- Lifecycle operation показывает намерение Lara, но не заменяет сведения о
  фактическом завершении процесса. Корреляция по instance, unit, времени и
  invocation не должна превращать непроверенный внешний restart в успешную
  ручную операцию.
- UDS в будущем показывает готовность приложения, а не является process
  supervisor. Потеря heartbeat сама по себе не равна падению процесса.

Причина инцидента хранится как нормализованное evidence и уровень уверенности.
Если systemd сообщает только факт завершения, причина остаётся `unknown`;
не следует выводить её из текста логов игрового сервера.

## Модель инцидента

Инцидент имеет стабильный ID, instance ID, идентичность unit/invocation,
время начала и восстановления, наблюдаемые состояния, evidence, ссылки на
связанные lifecycle operations и историю изменений. Отдельно хранятся:

- состояние отказа: `Open`, `Recovering`, `Resolved`;
- состояние разбора: `Unreviewed`, `Acknowledged`, `Investigated`.

Автоматический рестарт может перевести отказ в `Resolved`, но не меняет
`Unreviewed`. Повторная обработка одного факта не создаёт второй инцидент.
Состояние `not_observed` и временная потеря D-Bus не создают инцидент сами по
себе. Если восстановить историю невозможно, журнал фиксирует диагностический
пробел вместо выдуманного отказа.

## Доставка и доступ

MongoDB хранит инцидент и событие для повторной доставки. HTTP API выдаёт
историю с курсором; Socket.IO доставляет изменения состояния без требования
постоянного соединения клиента. Developer видит подробности всех доступных
инстансов. Admin и Challenger не получают auxiliary events. Политика общего
уведомления о restart primary из ADR-0001 остаётся отдельной задачей после
появления наблюдаемого primary. Backend проверяет роль на каждом запросе;
capability manifest служит навигации.

Точные HTTP DTO, ошибки, cursor и Socket.IO payload оформляются отдельным
контрактом до реализации endpoint. Изменение review state записывается в
аудит с actor ID и временем; автоматическое восстановление не выдаёт себя за
решение оператора.

## План реализации

1. Зафиксировать контракт инцидента, правила корреляции и матрицу доступа.
2. Добавить MongoDB repository, индексы, идемпотентную запись и outbox.
3. Подключить классификатор к существующему systemd observer и lifecycle
   operations; проверить ручной stop/restart, crash и automatic restart.
4. Реализовать journald replay с checkpoint и обработкой недоступного или
   ротированного журнала.
5. Добавить HTTP history/review, OpenAPI, manifest actions и Socket.IO
   projection с восстановлением через HTTP.
6. Расширить `doctor` и deployment guide требованиями к persistent journal
   и правам чтения для сервисной учётной записи Lara.
7. Проверить unit, MongoDB и Linux integration сценарии: падение между
   запусками Lara, повторный replay, auto-restart, разрыв D-Bus, отсутствие
   журнала, разграничение ролей и rollback.

После этого отдельно согласовать UDS handshake, heartbeat, таймауты и связь
с `InvocationID` с командой игрового плагина. Пилот primary и его перевод на
systemd требуют самостоятельного deployment окна.

## Критерии приёмки

- Падение и автоматический рестарт auxiliary оставляют один долговечный
  инцидент, который остаётся `Unreviewed` после восстановления.
- Перезапуск Lara или повторный journald replay не дублирует инциденты;
  повторная доставка события сохраняет тот же event ID для дедупликации
  клиентом.
- Плановый stop/restart Lara и внешний отказ различимы по evidence;
  неопределённый случай остаётся неопределённым.
- Потеря D-Bus, отсутствие первого snapshot и пробел journald не выдаются
  за падение игрового процесса.
- Developer может прочитать историю и отметить разбор; auxiliary-инциденты
  недоступны Admin и Challenger.
- Состояние можно восстановить через HTTP после пропущенных Socket.IO events.
- Primary остаётся работоспособным в режиме `external` без UDS-плагина и
  без принудительного перевода на systemd.

## Последствия

Релиз добавляет MongoDB collections, indexes и постоянный checkpoint для
наблюдателя. Для восстановления прошлых событий host должен сохранять
persistent journald и разрешать Lara читать нужные записи. При отсутствии
этих условий текущий systemd snapshot остаётся доступным, а пропущенный
интервал явно помечается как неполный.
